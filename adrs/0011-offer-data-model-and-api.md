# 11. Offer data model and API

- Status: Accepted
- Date: 2026-10-03

## Context

The first feature records the job offers the user responds to. The user asked for a title, a URL, a description and a creation date, plus any other field that is necessary. Interview steps (ADR-0004) will be attached to offers later and are out of scope here.

## Decision

### Model

An `Offer` (table `offers`, snake_case columns) has:

| Field         | Type                     | Required | Notes                                                                 |
| ------------- | ------------------------ | -------- | --------------------------------------------------------------------- |
| `id`          | UUID v7                  | yes      | Generated by the database layer; time-ordered.                        |
| `title`       | text, ≤ 200 chars        | yes      | Job title.                                                            |
| `company`     | text, ≤ 200 chars        | yes      | An offer is meaningless without the employer.                         |
| `url`         | http(s) URL, ≤ 2048      | no       | Some offers come from a recruiter or a referral and have no link.     |
| `location`    | text, ≤ 200 chars        | no       | City, country or "Remote".                                            |
| `description` | text, ≤ 20 000 chars     | no       | Pasted offer text; offers often disappear from job boards.            |
| `appliedAt`   | date (no time)           | no       | When the user responded; may differ from when the record was created. |
| `createdAt`   | timestamp with time zone | yes      | Set by the database.                                                  |
| `updatedAt`   | timestamp with time zone | yes      | Maintained by Prisma.                                                 |

Not included yet: salary, contract type and an overall status. The status will come from the interview process (ADR-0004); the others can be added when needed.

### API

REST resource `/offers` in the `OffersModule` of `back`:

- `POST /offers`: create, `201` with the offer.
- `GET /offers?limit=&offset=`: newest first (`createdAt` then `id`, descending). `limit` 1–100, default 20. Response `{ items, total, limit, offset }`.
- `GET /offers/:id`, `PATCH /offers/:id`, `DELETE /offers/:id` (`204`). Unknown or malformed ids answer `404` and `400`.
- `PATCH` is partial: an absent field is left unchanged, `null` clears an optional field; `title` and `company` cannot be `null`.
- Dates are exchanged as strings: `appliedAt` as `YYYY-MM-DD`, timestamps as ISO 8601.
- Request and response types live in `@emploi/shared` (ADR-0009); the DTO classes implement them.

## Consequences

- Validation rules (required fields, lengths, URL format) exist in the API DTOs and, for user feedback, in the front form schema (ADR-0012). The API stays the authority.
- Offset pagination is simple and enough for a personal history; it can move to cursor pagination if the list ever becomes large.
