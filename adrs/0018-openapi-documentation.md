# 18. OpenAPI documentation of the API

- Status: Accepted
- Date: 2026-10-04

## Context

The API has no documentation besides the code, the shared types (ADR-0009) and the ADRs. Developers (and tools) need a browsable, accurate description of its endpoints, parameters, bodies, responses and errors.

## Decision

- The API publishes an **OpenAPI 3** document generated by **`@nestjs/swagger`** from the controllers and DTOs, and serves **Swagger UI**:
  - `https://api.emploi.localhost/docs`: Swagger UI;
  - `https://api.emploi.localhost/docs-json`: the OpenAPI document.
- Documentation is enabled by the `API_DOCS_ENABLED` environment variable (default `true`), so an environment can turn it off.
- **Explicit decorators** (`@ApiProperty`, `@ApiOkResponse`…), not the Nest CLI Swagger plugin: the plugin only runs in `nest build`, while tests run with Vitest, which would see a different document. Explicit decorators give the same document everywhere.
- **Response classes implement the shared response types** (`OfferDto implements Offer`…), like the request DTOs implement the request types, so the compiler rejects documentation that drifts from what the API returns. Error responses (`400`, `404`) use one documented `ApiErrorDto`, the shape of NestJS errors.
- **The document is versioned** as `back/openapi.json`. An e2e test generates it and compares it to the committed file (Vitest file snapshot): a change to the API that doesn't update the file fails `make check`. `make openapi` regenerates it.

## Consequences

- API changes show up as diffs of `back/openapi.json` in review.
- Constraints are declared twice on request DTOs (class-validator for validation, `@ApiProperty` for documentation); the e2e tests on validation and the snapshot keep them honest.
- Swagger UI's static files ship in the back image (`swagger-ui-dist`).
- The front keeps using `@emploi/shared`; generating a client from the document is possible later and would get its own ADR.
